## 010. 2026-10-11 22:50:00 JST — アシスタント

**参照元のUIと学習の流れを引き継ぎ、React＋TypeScript＋Viteの静的アプリとして作る方針をおすすめします。** 構成は単一アプリにまとめ、問題データの品質確認と、リリース後の変更記録に必要な仕組みを用意します。

いただいた回答を踏まえた検討結果です。まだ実装・問題データ作成・リポジトリの変更には着手していません。

**1．収録範囲と機能**

IPAの各年度ページを確認したところ、現在の収録対象は**2009〜2025年度の17回、計425問**です。2011年度は特別試験、2020年度は10月試験として扱います。参照元のSAとは異なり、PMには2020年度の公開問題があります。[IPA過去問題一覧](https://www.ipa.go.jp/shiken/mondai-kaiotu/index.html)、[2020年度の公開資料](https://www.ipa.go.jp/shiken/mondai-kaiotu/2020r02.html)

引き継ぐ機能は次のとおりです。

- 年度の一覧から選び、問題画像を1問ずつ表示
- ア〜エを選択し、結果確認後に正誤・正答・解説を表示
- 前後移動、問題番号による移動、一括採点
- 問題へのチェックと、年度単位の回答クリア
- 回答・現在の問題・チェックをブラウザ内に保存

採点済みの回答は固定し、未回答は一括採点の対象にせず、回答クリア後もチェックは残す、という参照元の操作も継承します。[参照元の仕様](https://github.com/rabut001/system-arch-training/blob/main/AGENTS.md)

なお、2026年度のPMはCBT方式で、従来の午前Ⅱに相当する名称は「科目A-2」です。アプリはご依頼どおり午前Ⅱの過去問演習を中心にし、説明に現行名称を補います。2026年度分は、IPAが問題・正解を公開した場合に追加します。[IPAのPM試験案内](https://www.ipa.go.jp/shiken/kubun/pm.html)

**2．UIは継承し、読みやすさを改善**

参照元の落ち着いた背景色、青の選択表示、正誤の色と記号、年度一覧と演習画面の構成を引き継ぎます。

ソースと最近の改修資料を見ると、改善の中心は**問題画像を読む領域と、解説を読む領域の確保**です。以下を提案します。[参照元の表示領域の改修資料](https://github.com/rabut001/system-arch-training/blob/main/specs/0003-question-image-height/README.md)

| 改善案 | 得られる効果 |
|---|---|
| スマートフォンで問題画像を拡大できるようにする | 小さい文字・表・図を読める |
| PCの広い画面では、問題を左、回答・解説を右に配置 | 問題と解説を照らし合わせやすい |
| 主操作を強調し、一括採点・クリアを補助操作として整理 | 次に押すボタンが分かりやすい |
| 解説を「正解の根拠」「各選択肢」「計算手順」に区切る | 必要な説明を探しやすい |
| フォーカス表示、状態の読み上げ、保存失敗の通知を整える | キーボード操作や保存時の安心感が向上する |

**初回から、この改善を含める案をおすすめします。** 年度ごとに1問ずつ解く基本構造や採点ルールはそのままです。最新年度の実問題を使った画面で、配置と読みやすさをご確認いただく段階を設けます。

**3．技術とリポジトリ構成**

2026年10月時点の公式資料と、このアプリの要件から、次の構成が適切と判断します。

| 項目 | 提案 |
|---|---|
| アプリ | React＋TypeScript＋Vite |
| スタイル | 通常のCSS |
| 状態管理 | React標準機能＋localStorage |
| 公開 | GitHub ActionsからGitHub Pages |
| 問題抽出 | Python＋PyMuPDF、必要なPDFにはOCR |
| 開発環境 | Node.js 24 LTS、npm、lockfileを保存 |
| 検証 | データ検証、採点・保存のテスト、少数のブラウザテスト |

React公式にはViteによる構築方法があり、Vite公式にはGitHub Pagesへの公開手順があります。今回の画面数と静的データの扱いなら、この構成で十分です。Node.jsは現時点のLTSを採用します。[React公式](https://react.dev/learn/build-a-react-app-from-scratch)、[Vite公式](https://vite.dev/guide/static-deploy.html)、[Node.jsリリース情報](https://nodejs.org/en/about/previous-releases)

構成案は次のとおりです。アプリをリポジトリ直下で管理し、標準的なViteの配置に合わせます。

```text
project-manager-training/
├─ src/                         # 画面、採点、進捗保存
├─ public/
│  └─ data/
│     ├─ index.json             # 収録回一覧
│     └─ <exam-id>/
│        ├─ questions.json      # 問題・正解・解説
│        └─ q01.png ...         # 問題画像
├─ sources/
│  └─ ipa/
│     ├─ manifest.json          # 出典URL、取得日、PDFの識別情報
│     └─ <exam-id>/             # 午前Ⅱの問題・解答PDF
├─ scripts/                     # 取得、抽出、データ検証
├─ tests/                       # 採点・保存・主要操作のテスト
├─ docs/
│  └─ product.md                # 現在の製品仕様
├─ specs/
│  ├─ README.md                 # 案件一覧と運用ルール
│  ├─ _template.md              # 変更案件のひな形
│  └─ 0001-initial-release/
│     ├─ README.md              # 初回開発の計画・確認結果
│     └─ review/                # 年度別の問題・解説確認記録
├─ .github/workflows/           # 検証とPages公開
├─ AGENTS.md                    # 開発時の作業ルール
├─ README.md                    # 起動、更新、公開、復旧手順
├─ package.json
└─ package-lock.json
```

この配置なら、公開データを別フォルダから配信する独自処理を減らせます。原本は午前Ⅱの問題・解答PDFだけを保存し、問題画像と確認済みJSONもGitで管理します。通常のUI改修では、問題抽出環境を起動せずに作業できます。

**4．過去問の抽出と解説作成**

ここが作業量の中心です。425問について、抽出・執筆・確認を分けて進めます。

1. **原本取得**  
   午前Ⅱの問題・解答PDFを取得し、年度・実施期・URL・取得日を記録します。
2. **問題抽出**  
   参照元の切り出し処理を参考に画像化します。図表、選択肢、ページをまたぐ問題の欠落を確認し、自動処理で難しい箇所は切り出し範囲を指定して補正します。
3. **問題文と正解の照合**  
   解説作成用に問題文・選択肢をテキスト化し、原画像と照合します。正解はIPAの解答PDFから取得します。
4. **解説作成**  
   正解の根拠、各誤答の理由、必要な用語・前提・計算手順を説明します。
5. **別工程で再確認**  
   作成したその場で確認済みにはせず、原問題・公式正解・根拠資料に戻って確認します。年度別に記録を残します。

解説では、特に次を重視します。

- 選択肢の言い換えだけで終わらせない
- 計算は式・代入・結果を示す
- 数値の誤答が作られた理由を推測で説明しない
- PMBOKなどの版や、出題当時の制度を現在の説明と混同しない
- 法令・契約・規格などは根拠を確認し、必要な参照先を残す
- アプリ内で「IPAの公式解説ではない」と明記する

問題の出典は年度・期・試験区分・午前Ⅱ・問番号まで表示します。これはIPAの利用条件にも沿います。[IPAの過去問題利用上の留意点](https://www.ipa.go.jp/shiken/faq.html)

再抽出時に、執筆・確認済みの解説を上書きしない仕組みにします。

**5．リリース後の改修管理**

参照元の`specs`の考え方は継承し、**現在の仕様と、変更案件の履歴を分ける**構成にします。

- 現在の仕様は`docs/product.md`に集約
- UI変更、問題追加、解説修正などは`specs/0002-.../`として記録
- 各案件は原則1つのMarkdownに、目的・変更内容・対象・確認結果を記載
- 大量の問題確認だけ、年度別の確認ファイルを追加
- 完了した案件は固定し、後日の修正は新しい案件にする

改修は「変更内容を記録 → 実装・データ修正 → 必要な確認 → 公開 → 完了記録」の流れです。仕様が変わる場合は現行仕様も更新します。問題IDと保存データ形式を安定させ、改修で学習進捗が消えないようにします。

**6．実装に進む場合の順序と完了条件**

| 段階 | 成果物・確認内容 |
|---|---|
| ① 仕様・構成を確定 | 現行仕様、初回案件、データ形式、解説の確認基準 |
| ② 最新年度で一通り作成 | 25問の抽出・解説と、スマートフォン／PCの演習画面 |
| ③ 画面と解説の見本を確認 | 配置、読みやすさ、説明の詳しさを調整 |
| ④ 残り16回を収録 | 全425問の画像・正解・解説と確認記録 |
| ⑤ 検証・リリース準備 | データ検証、主要操作、再読み込み、直接URL、公開成果物を確認 |

完了条件は、**全425問の内容確認が済み、主要操作・進捗保存・スマートフォンとPCでの表示が確認でき、公開と改修の手順が文書化されていること**です。

アプリの実装は小さく保てますが、全問の解説作成・確認には相応の作業があります。最新年度の25問で品質基準を固めてから全年度へ展開する進め方が、今回の規模には適切です。

## 012. 2026-10-11 22:59:29 JST — アシスタント

スマートフォン中心の方針で、**問題画像の拡大を今回の実装に含めます。** PCでも縦並びを維持し、解説は現在と同じコンパクトな文章表示にします。

**主操作の強調は、ボタンの見た目を中心に変える想定です。** 配置や高さを保ち、画面の消費を増やさない範囲にします。

| 操作 | 具体的な変更 |
|---|---|
| 結果を確認 | 選択後、青地・白文字にして次の操作を明確にする |
| 前へ・次へ | 現在の白地・枠線のボタンを維持する |
| 一括採点 | 下部の配置を維持し、白地・枠線で表示する |
| 回答をすべてクリア | 下部の配置を維持し、控えめな赤文字で区別する |

一括採点・クリアの実行前に出る確認画面も継承します。主操作の強調については、**この見た目の調整だけ**をおすすめします。

**フォーカス表示・読み上げ・保存失敗の通知は、次の内容です。**

- **フォーカス表示**  
  キーボードで操作するとき、操作対象のボタンに輪郭線を表示します。要素の大きさや配置は変わりません。通常のタップ操作時には表示しません。

- **状態の読み上げ**  
  スクリーンリーダー利用時に「問3、チェック済み、誤答」「選択肢イ、選択中」などが分かるようにします。参照元の対応を引き継ぎ、採点直後に正誤・正答を短く通知する対応を補います。画面上の説明は増やしません。
